**Centralized Mock API Server for the emarket Platform**

## 1. Overview

`emarket-mock-api` is a centralized HTTP API mocking service for the emarket platform.

It simulates HTTP responses from `emarket-api-gateway`, allowing frontend applications to be developed, tested, and integrated before the actual backend services are implemented.

The project uses **WireMock** as its HTTP mocking engine.

It provides predefined API endpoints, request matching rules, HTTP response codes, response headers, and JSON response bodies.

The service is designed to support multiple frontend clients:

- `emarket-web` — React + TypeScript + Vite.
- `emarket-mobile` — future mobile application.

Both clients can use the same mock API definitions and API contracts.

### 1.1. Main Objectives

- Enable frontend development independently of backend availability.
- Provide realistic HTTP API responses.
- Maintain consistent API contracts across frontend clients.
- Support successful and unsuccessful API scenarios.
- Simulate authentication and authorization responses.
- Support request validation and error handling.
- Provide a centralized source of mock API definitions.
- Support local development and Docker-based execution.
- Simplify frontend integration testing.

### 1.2. Non-Goals

The project is not intended to:

- Implement actual business logic.
- Replace `emarket-api-gateway`.
- Replace `emarket-bff-web`.
- Implement authentication or authorization.
- Persist actual user or business data.
- Connect to databases.
- Implement production business workflows.

All responses are predefined or dynamically generated by WireMock.

## 2. Architecture

### 2.1. High-Level Architecture

```text
                       emarket Platform
                              |
                              |
                 +------------+------------+
                 |                         |
                 v                         v
           emarket-web              emarket-mobile
          React + TypeScript          Future Client
                 |                         |
                 +------------+------------+
                              |
                              | HTTP / HTTPS
                              |
                              v
                    emarket-mock-api
                         WireMock
                              |
                  +-----------+-----------+
                  |                       |
                  v                       v
               Mappings              Response Bodies
             (JSON rules)               (JSON)
```

`emarket-mock-api` acts as a simulated backend API endpoint.

Frontend applications interact with it using the same HTTP methods, paths, request headers, query parameters, and request bodies expected from the actual API Gateway.

### 2.2. Relationship with API Gateway

The mock service simulates the external API contract exposed by `emarket-api-gateway`.

```text
Frontend Client
      |
      |
      v
+---------------------+
| API Base URL        |
+---------------------+
      |
      |
      +----------------------------+
      |                            |
      v                            v
+-------------------+     +-------------------+
| emarket-mock-api  |     | emarket-api-      |
| WireMock          |     | gateway           |
+-------------------+     +-------------------+
      |                            |
      v                            v
 Predefined JSON              Actual Backend
 Responses                    Services
```

Only one backend target is active for a given frontend environment.

The frontend API client should not depend on whether the response comes from WireMock or the actual API Gateway.

### 4.2. Mappings

The `mappings/` directory contains WireMock mapping definitions.

Each mapping describes:

- Mapping name.
- HTTP method.
- URL or URL path.
- Query parameters, if required.
- Request headers, if required.
- Request body matching rules, if required.
- HTTP response status.
- Response headers.
- Response body or response body file.

### 4.3. Response Bodies

The `__files/` directory contains reusable JSON response bodies.

Keeping response bodies separate from mappings provides:

- Better maintainability.
- Easier JSON editing.
- Reusable response definitions.
- Clear separation between HTTP behavior and test data.

## 5. API Contract

### 5.1. API Base Path

All mocked endpoints follow the Stage 1 API contract:

```text
/api/v1/web/**
```

The mock server does not implement frontend routes. It only simulates backend HTTP API endpoints.

### 5.2. Authentication API

| HTTP Method | Endpoint | Description |
|---|---|---|
| POST | `/api/v1/web/auth/register` | User registration |
| POST | `/api/v1/web/auth/login` | User authentication |
| POST | `/api/v1/web/auth/logout` | User logout |
| POST | `/api/v1/web/auth/refresh` | Refresh authentication tokens |
| GET | `/api/v1/web/auth/me` | Get authenticated user |
| POST | `/api/v1/web/auth/forgot-password` | Request password recovery |
| POST | `/api/v1/web/auth/reset-password` | Reset password |

### 5.3. User Profile API

| HTTP Method | Endpoint | Description |
|---|---|---|
| GET | `/api/v1/web/users/me` | Get current user profile |
| PATCH | `/api/v1/web/users/me` | Update current user profile |

### 5.4. User Addresses API

| HTTP Method | Endpoint | Description |
|---|---|---|
| GET | `/api/v1/web/users/me/addresses` | Get user addresses |
| POST | `/api/v1/web/users/me/addresses` | Create address |
| GET | `/api/v1/web/users/me/addresses/{addressId}` | Get address by ID |
| PATCH | `/api/v1/web/users/me/addresses/{addressId}` | Update address |
| DELETE | `/api/v1/web/users/me/addresses/{addressId}` | Delete address |

### 5.5. User Preferences API

| HTTP Method | Endpoint | Description |
|---|---|---|
| GET | `/api/v1/web/users/me/preferences` | Get user preferences |
| PATCH | `/api/v1/web/users/me/preferences` | Update user preferences |

**Note:** This API scope corresponds to Stage 1. Future product, cart, order, and payment APIs should be introduced in their respective development stages.

## 6. Mock Response Design

### 6.1. Mapping Example

File:

`wiremock/mappings/auth/post-login.json`

```json
{
  "name": "User login",
  "request": {
    "method": "POST",
    "urlPath": "/api/v1/web/auth/login"
  },
  "response": {
    "status": 200,
    "headers": {
      "Content-Type": "application/json"
    },
    "bodyFileName": "auth/login-success.json"
  }
}
```

### 6.2. Response Body Example

File:

`wiremock/__files/auth/login-success.json`

```json
{
  "user": {
    "id": "user-001",
    "email": "user@example.com",
    "firstName": "John",
    "lastName": "Doe",
    "roles": [
      "USER"
    ]
  },
  "accessToken": "mock-access-token",
  "expiresIn": 900
}
```

The example represents a simulated successful authentication response.

Tokens are mock values and must never be treated as real authentication credentials.

### 6.3. Error Response Example

File:

`wiremock/__files/common/unauthorized.json`

```json
{
  "timestamp": "2026-01-01T10:00:00Z",
  "status": 401,
  "error": "Unauthorized",
  "message": "Authentication is required.",
  "path": "/api/v1/web/users/me"
}
```

### 6.4. HTTP Status Codes

The mock API should support the following response scenarios:

| Status | Description |
|---|---|
| 200 | Successful request |
| 201 | Resource created |
| 204 | Successful request without response body |
| 400 | Bad request / validation error |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Resource not found |
| 409 | Resource conflict |
| 429 | Too many requests |
| 500 | Internal server error |
| 503 | Service unavailable |

Each scenario should be explicitly defined through WireMock mappings.

### 6.5. Request Matching

Mappings should use appropriate request matching rules.

Examples:

- HTTP method.
- URL path.
- Query parameters.
- Content-Type.
- Authorization header.
- JSON request body.
- JSONPath expressions.

For endpoints with multiple scenarios, use explicit matching criteria and mapping priorities to avoid ambiguous matches.

### 6.6. Response Templating

WireMock response templating can be enabled when dynamic responses are required.

Possible use cases:

- Dynamic timestamps.
- Echoing request values.
- Generating response identifiers.
- Reusing request data in error responses.

Static JSON responses should remain the default approach.

## 7. Execution Modes

The project supports two independent execution modes.

Both modes use the same WireMock mappings and response bodies.

### 7.1. DEV Mode — Host Machine

**Purpose:** Local frontend development without running WireMock inside Docker.

Architecture:

```text
+--------------------------+
| Ubuntu Host Machine      |
|                          |
|  +--------------------+  |
|  | emarket-web        |  |
|  | React + Vite       |  |
|  | localhost:5173     |  |
|  +--------------------+  |
|            |             |
|            v             |
|  +--------------------+  |
|  | emarket-mock-api   |  |
|  | WireMock Standalone|  |
|  | localhost:9090     |  |
|  +--------------------+  |
|                          |
+--------------------------+
```

**Requirements:**

- Ubuntu 24.04 or compatible operating system.
- Java 21.
- WireMock Standalone JAR.
- Git.

**Configuration:**

| Parameter | Value |
|---|---|
| Execution | Host Machine |
| Runtime | Java 21 |
| Port | 9090 |
| Root Directory | `./wiremock` |
| Base URL | `http://localhost:9090` |

**Startup:**

```bash
./scripts/dev-start.sh
```

**Stop:**

Press `Ctrl+C` in the terminal running WireMock.

**Health check:**

```bash
curl http://localhost:9090/__admin/health
```

**Example API request:**

```bash
curl http://localhost:9090/api/v1/web/users/me
```

**Purpose:** Run WireMock as an isolated Docker container.

|                                  |

**Requirements:**

**Configuration:**

| Parameter | Value |

| Feature | DEV | DEPLOY |
|---|---|---|

## 8. Docker Configuration

### 8.1. Docker Compose

File: `docker-compose.yml`

```yaml
services:
  emarket-mock-api:
    image: wiremock/wiremock:${WIREMOCK_VERSION}
    container_name: emarket-mock-api

    ports:
      - "${MOCK_API_PORT:-9090}:8080"

    command:
      - "--port=8080"
      - "--global-response-templating"

    volumes:
      - ./wiremock:/home/wiremock

    restart: unless-stopped
```

The WireMock image version must be pinned to a specific tested version.

### 8.2. Environment Variables

File: `.env.example`

```dotenv
WIREMOCK_VERSION=<pinned-wiremock-version>
MOCK_API_PORT=9090
```

The actual `.env` file must not be committed to Git.

### 8.3. Docker Networking

When frontend applications run inside Docker, they should communicate with WireMock through the Docker network.

Example:

```text
emarket-web:5173
      |
      | Docker Network
      |
      v
emarket-mock-api:8080
```

When the frontend runs directly on the host machine, it can use:

```text
http://localhost:9090
```

## 9. Frontend Integration

### 9.1. emarket-web

`emarket-web` uses the mock API as an alternative backend target.

The frontend should use a single API client and a configurable API base URL.

Example:

```typescript
export const API_CONFIG = {
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 10000,
} as const;
```

For local development with WireMock:

```dotenv
VITE_API_BASE_URL=http://localhost:9090/api/v1
```

Alternatively, Vite can proxy `/api` requests to WireMock.

Example:

```typescript
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:9090',
      changeOrigin: true,
    },
  },
},
```

With this approach, frontend requests use relative paths:

```typescript
GET /api/v1/web/users/me
```

### 9.2. Switching Between Mock and Actual Backend

```text
                  emarket-web
                       |
                       |
                  API Client
                       |
                       |
                Configurable URL
                       |
             +---------+---------+
             |                   |
             v                   v
         WireMock             API Gateway
       localhost:9090       localhost:8080
             |                   |
             v                   v
       Mock Responses        Real Backend
```

Switching backend targets should not require changes to frontend business logic or API service implementations.

### 9.3. emarket-mobile

The future `emarket-mobile` application can use the same API contracts.

The mobile client should configure its own API base URL according to its execution environment.

Examples:

- Android Emulator: `http://10.0.2.2:9090`
- iOS Simulator: `http://localhost:9090`
- Physical device: host machine IP address, subject to network configuration.

The mobile application should not depend on Web-specific implementation details.

## 10. Testing Strategy

The project should provide basic automated verification of mock API definitions.

### 10.1. JSON Validation

Validate all JSON mapping and response files.

Checks should include:

- Valid JSON syntax.
- Valid WireMock mapping structure.
- Correct file references.
- No duplicate or conflicting mappings.

### 10.2. Smoke Tests

After WireMock starts, execute basic HTTP requests.

Example:

```bash
curl -f \
  http://localhost:9090/api/v1/web/users/me
```

Verify:

- Expected HTTP status.
- Content-Type header.
- Valid JSON response.
- Required response fields.

### 10.3. API Scenario Testing

Each important endpoint should have tests for:

- Successful responses.
- Validation errors.
- Unauthorized requests.
- Forbidden requests.
- Missing resources.
- Server errors.

### 10.4. CI Pipeline

Recommended GitHub Actions workflow:

```text
Git Push / Pull Request
          |
          v
     JSON Validation
          |
          v
    WireMock Startup
          |
          v
      Smoke Tests
          |
          v
    Docker Build Check
          |
          v
      CI Success
```

The pipeline should validate mock definitions before changes are merged into the main branch.

## 11. Development Guidelines

### 11.1. Mapping Naming Convention

Use the following naming convention:

```text
{http-method}-{resource}.json
```

Examples:

```text
post-login.json
get-current-user.json
patch-current-user.json
delete-address.json
```

Use lowercase kebab-case for file names.

### 11.2. Mapping Organization

Group mappings by business domain:

```text
mappings/
├── auth/
├── users/
├── addresses/
└── preferences/
```

### 11.3. Response Body Organization

Keep response bodies grouped by domain:

```text
__files/
├── common/
├── auth/
├── users/
├── addresses/
└── preferences/
```

### 11.4. API Contract Consistency

All mappings must follow the agreed API contract of `emarket-api-gateway`.

Changes to endpoint paths, HTTP methods, request structures, or response structures should be coordinated with frontend and backend development.

### 11.5. No Client-Specific Duplication

Do not create duplicate mappings for Web and Mobile when both clients use the same API contract.

If different BFF contracts are introduced in the future, separate mappings by API scope.

### 11.6. Test Data

Use fictional test data only.

Never commit:

- Real user credentials.
- Real access tokens.
- Real refresh tokens.
- Personal information.
- Production API keys.
- Production secrets.

## 13. Security Considerations

Although the mock server does not implement actual authentication, it should follow basic security practices.

- Do not expose the WireMock administrative API publicly.
- Restrict access to the mock server in shared environments.
- Do not use production credentials or tokens.
- Do not expose mock administration endpoints to frontend clients.
- Avoid committing secrets.
- Do not use mock responses as evidence of real authorization.
- Do not expose Docker management interfaces.
- Restrict network access to the container where appropriate.

WireMock's administrative endpoints under `/__admin` should be available only to developers and authorized automation.

## 16. Final Architecture Decisions

The following decisions define the initial architecture of `emarket-mock-api`.

| Decision | Selected Approach |
|---|---|
| Repository | Separate GitHub repository |
| Mocking Engine | WireMock |
| Runtime | Java 21 |
| Configuration Format | JSON |
| Response Format | JSON |
| Local Execution | WireMock Standalone |
| Container Execution | Official WireMock Docker Image |
| Container Orchestration | Docker Compose |
| Mock Definitions | Shared across execution modes |
| API Contract | `emarket-api-gateway` |
| Frontend Clients | Web and future Mobile |
| CI/CD | GitHub Actions |
| Business Logic | Not implemented |
| Database | Not required |

**Core principle:**

`emarket-mock-api` is a centralized, reusable mock backend that enables independent frontend development while preserving consistency with the actual emarket API contracts.

It provides one source of mock API definitions and supports multiple execution environments without duplicating implementation.
